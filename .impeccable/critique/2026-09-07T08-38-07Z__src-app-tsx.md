## Design Specificity Verdict

**Authored for this product, with real evidence of drift toward the generic where later work took the path of least resistance.** The wire/dispatch metaphor isn't skin-deep: precedence stamps drive typography weight rather than color, the JetBrains Mono "machine voice" is applied with discipline, and the expired-mitigation alarm state — confirmed live, not just in a marketing screenshot — is genuinely distinctive: a solid alarm-red block reading "MITIGATION EXPIRED 00:58 AGO — UNWIND REQUIRED" with a tabular-numeral countdown recomputed in real time.

But two documented, code-verifiable gaps pull toward the generic:
- `src/components/shared/Modal.tsx` — by its own code comment, "the one modal shell for the whole app" — is a centered dialog with a `bg-black/60` backdrop, a stock SaaS pattern that directly contradicts DESIGN.md's own "Slide-Over Panel (signature pattern)" section, which names the new-incident form as sharing one right-docked shell with the incident detail view.
- Three secondary screens (User Directory, Past Incidents, Audit Log) each swap the "POSTMORTEM" nameplate for their own screen title, contradicting DESIGN.md's explicit "one visual anchor across every top-level screen" line.

**Deterministic scan (Assessment B):** The static CLI pass (`detect.mjs --json src`, 63 files) came back genuinely clean — 0 findings, confirmed twice (once with `--no-config` to rule out a suppression, once via direct spot-check) — so nothing here is a source-level anti-pattern the regex engine can catch. The browser-injected overlay pass, which reads actual computed styles at runtime, is where the real findings are: 11px text with 0.20em tracking on the secondary-screen subtitles, wide letter-spacing on assignee/meta labels, and cramped padding on the auth tab toggle — all confirmed via on-page overlay boxes across the landing page, login, incident desk, detail panel, and admin directory. This is exactly the "detector caught issues the LLM missed" case: Assessment A's holistic read never flagged these, because they're invisible in source and only surface once Tailwind's arbitrary-value classes resolve to real computed pixels. One likely false positive: `buried-raster` findings on `keeper-lock#...` elements are a third-party password-manager browser extension injecting its own lock icon into the password field — not app markup, won't reproduce for users without that extension.

## Overall Impression

The wire-desk world holds up in its signature moments — the alarm state, the keyboard-shortcut hints — but two systemic consistency violations (the dual panel-shell pattern, the vanishing masthead) undercut the "one system" story DESIGN.md itself tells, and a handful of small-but-real runtime typography/spacing defects show the system isn't being mechanically enforced everywhere it claims to be. The single biggest opportunity is reconciling `Modal.tsx` against the slide-over pattern — it's the one fix that resolves the most-cited inconsistency across both the heuristic scoring and the power-user persona walkthrough. Score moved from 27/40 (2026-09-04, scoped only to the pre-multi-tenancy `App.tsx` flow) to 24/40 today — not a regression so much as a much larger surface (landing page, invite flow, admin/audit screens, multi-tenancy) getting real scrutiny for the first time, surfacing genuine new gaps the narrower prior pass couldn't have seen.

## What's Working

1. **Keyboard-shortcut hints printed directly on the controls** (`[M]`, `[R]`, `[U]`) — costs nothing for anyone who ignores it, directly serves the product's "speed of action beats completeness" principle.
2. **The expired-mitigation alarm state**, confirmed live: solid alarm-red block, tabular-numeral countdown recomputed in real time — exactly the "ICU-grade legibility" the brief calls for, not just a mockup promise.
3. **The static/mechanical layer is genuinely clean.** Zero source-level anti-patterns across 63 files — the design tokens and component patterns that exist in source are being followed correctly; the gaps that exist are either runtime-only (caught by Assessment B's browser pass) or structural/pattern-level (caught by Assessment A's review), not sloppy implementation.

## Priority Issues

**[P1] Raw backend/API text surfaces as a user-facing error**
- **What:** Trying to RESOLVE an incident with an active mitigation returns, verbatim, in the panel: "Cannot resolve an incident with an active mitigation. Clear the mitigation first via DELETE /incidents/{incident_id}/mitigation."
- **Why it matters:** This is a triage tool used "often at unsociable hours" under acute time pressure. A responder who doesn't recognize a REST path as "click the button above me" stalls or escalates over something the UI already solves in one click — confirmed as a directly reproducible, natural-order-of-operations edge case (Riley persona), not a contrived one.
- **Fix:** Catch this specific server rejection and render an actionable message ("An active mitigation is blocking resolution — unwind it first"), or disable/relabel RESOLVE when a mitigation is active and route straight to Unwind.
- **Suggested command:** `/impeccable clarify`

**[P1] Two incompatible panel shells for one documented pattern**
- **What:** `IncidentDetailPanel.tsx` correctly implements DESIGN.md's right-docked slide-over. `NewIncidentPanel.tsx` and `InviteUserPanel.tsx` both route through `shared/Modal.tsx` — a centered, backdrop-dismissible dialog — despite DESIGN.md stating the new-incident form "shares one shell" with the incident detail view.
- **Why it matters:** A user learns "panels dock right, close top-right" from claiming/mitigating incidents within the first minute, then hits a completely different interaction model — centered, click-outside-to-dismiss — on two of the product's most common actions (file an incident, invite a user). This is Heuristic 4's "similar things behave differently" failure on two high-frequency flows, not an edge case.
- **Fix:** Either rebuild `NewIncidentPanel`/`InviteUserPanel` onto the same right-docked shell as `IncidentDetailPanel`, or explicitly amend DESIGN.md to define "create" panels as a second, intentional pattern — the code and the docs need to agree either way.
- **Suggested command:** `/impeccable shape`

**[P2] Masthead nameplate disappears on every secondary screen**
- **What:** `WireHeader.tsx` renders "POSTMORTEM" (Orbitron). `AdminUsersScreen.tsx`, `PastIncidentsScreen.tsx`, and the Audit Log screen each render their own screen title in the identical treatment instead — confirmed live and in source on all three.
- **Why it matters:** DESIGN.md calls this nameplate "the single persistent chrome element" and names the admin directory specifically as repeating it to keep "one visual anchor across every top-level screen." As shipped, the brand anchor disappears everywhere except the wire desk and login.
- **Fix:** Restore "POSTMORTEM" as a persistent small-caps wordmark on these screens with the current screen title as the subtitle (matching how the login screen already does it), or update DESIGN.md to describe the contextual-title pattern as intentional.
- **Suggested command:** `/impeccable polish`

**[P2] Status tag and mitigation alarm can visually disagree**
- **What:** Once a mitigation's TTL expires, the incident's status tag keeps reading MITIGATED in nominal green — "still live, working as expected" per DESIGN.md's own color rule — directly above a solid alarm-red banner reading "UNWIND REQUIRED."
- **Why it matters:** A responder triaging at a glance is trained by this exact design system to trust the status tag as the top-level read. Right now that glance can say "green, fine" one line above a banner saying "needs a human now."
- **Fix:** Introduce a fourth status-tag treatment (e.g., amber "MITIGATED — EXPIRED") once TTL lapses, so the corner tag and the mitigation readout never contradict each other.
- **Suggested command:** `/impeccable clarify`

**[P2] Real typography/spacing defects only visible at runtime**
- **What:** Browser-injected evidence found 11px text at 0.20em tracking on secondary-screen subtitles (below DESIGN.md's own Label spec), wide letter-spacing on assignee/meta labels, and cramped padding on the SIGN IN/REGISTER tab toggle — confirmed via on-page overlay across five separate surfaces. The static source scan cannot see this class of defect at all (0 findings, genuinely clean).
- **Why it matters:** These are exactly the token violations DESIGN.md claims are enforced everywhere; they exist only because Tailwind's arbitrary-value classes (`text-[11px]`, custom tracking) bypass the documented scale, and nothing catches that at the source level.
- **Fix:** Audit the flagged elements against DESIGN.md's Label typography spec and 44px control-height rule; prefer the documented scale classes over arbitrary values.
- **Suggested command:** `/impeccable polish`

## Persona Red Flags

**Alex (Power User):** The `[M]`/`[R]`/`[U]` shortcuts are genuinely good, but there's no shortcut for CLAIM — the first action on every new incident, breaking the pattern Alex would expect from the rest of the panel. More concretely: Alex learns "panels dock right" from the incident detail view in the first minute, then hits a centered, backdrop-dismissible dialog for File Incident and Invite User — a jarring model switch on two of the most-used flows (same root cause as the P1 above). The SERVICE field on the new-incident form is also raw free text with no autocomplete against previously-used values, so a fast typist filing their fifth `payments-api` incident this week has nothing stopping them from fat-fingering `payments-service` and quietly fragmenting incident history.

**Sam (Accessibility-Dependent User):** Severity and status are both carried by text labels, not color alone, matching the product's own commitment. The red flag: when the resolve-blocked error fires, nothing ties it programmatically to the UNWIND MITIGATION control that actually resolves it — a screen-reader user gets the same disconnected REST-path text with no easier path to the fix than a sighted user has, arguably harder since they can't visually re-scan the panel. Assessment B's 11px-text finding reinforces this from a low-vision angle too — text below common accessibility-friendly minimums on three screens. Tab order wasn't exhaustively verified this pass, so gaps beyond these can't be ruled out.

**Riley (Stress Tester):** Directly reproduced the resolve-blocked raw-API-text issue above as a natural order-of-operations edge case, not a contrived one. Separately: PostMortem stores its JWT in `localStorage` under one key, shared per browser origin across all tabs — signing into a second account in another tab silently swaps the session for every open tab on next navigation, with no "you've been signed out" notice. For a product explicitly built around "responders collaborating on the same incident concurrently," a shared on-call workstation hitting this is a plausible real scenario worth a deliberate look, not just a testing artifact.

## Minor Observations

- The password field's visibility-toggle icon has no confirmed accessible name/label.
- "Must be at least 12 characters" helper text is static — doesn't confirm once satisfied.
- Mitigation TTL is a bare number input with no quick-select presets (15/30/60); a stray digit at 2am could set an hours-long TTL with no confirmation step.
- Neither Past Incidents nor the Audit Log has a date filter or search; the Audit Log currently shows everything on one unpaginated screen.
- Version-conflict copy ("Expected version 4, but current version is 5") is honest per the product's "make concurrency visible" principle, but is pure developer language — could pair the numbers with one plain-language clause.
- A `transition: padding` on `body` was flagged on every single page tested (6/6) by the browser pass — consistent enough it's likely one systemic base style rather than six independent defects; root cause not confirmed, worth a quick look but not urgent.
- The detector's own console output showed a count/label mismatch on one screen (header said 3 findings, 4 log lines followed) — a tooling anomaly worth a heads-up, not a product issue.
- Mobile-width (~390px) live verification couldn't be completed in this pass (a `resize_window` limitation already hit earlier in this session too); mobile behavior for the detail panel was confirmed at the source level instead (`sm:` breakpoint promotes from full-width bottom dock to right-hand panel, matching DESIGN.md), not visually live.

## Questions to Consider

1. Given DESIGN.md states the new-incident form and the incident detail panel "share one shell," should `NewIncidentPanel` and `InviteUserPanel` be rebuilt onto that same right-docked pattern — or should the docs be relaxed to admit a legitimate second "create" pattern? Right now the code and the spec disagree.
2. The product's principle is "make concurrency visible, not hidden" for version conflicts — should the resolve-blocked-by-mitigation state get that same first-class treatment (a dedicated banner + one-click resolve-after-unwind) instead of a raw validation string?
3. Should incident status reflect mitigation freshness — an amber/alarm variant of MITIGATED once TTL lapses — so the corner status tag and the alarm banner beneath it never tell a responder two different things at a glance?
